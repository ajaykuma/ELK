Explaination:
current_node gives details about the node:
id: Elasticsearch internal node ID
transport_address: node network address
attributes: node properties like ML memory, X-Pack installed, etc.

Allocation decisions:
can_remain_on_current_node: yes → shard can safely stay on node3.
can_rebalance_cluster: yes → ES can try to rebalance the cluster, but:
   can_rebalance_to_other_node: no → cannot move this shard to any other node.
   rebalance_explanation explains why it cannot move:
          “no target node exists that can both allocate this shard and improve the cluster balance”
          Meaning either other nodes already have this shard or moving it wouldn’t improve cluster balance.

Node Allocation decisions:
ES evaluates each node to see if the shard can be allocated there.

Example: node2
node_decision: no → shard cannot go here
decider: same_shard → the reason
explanation: node2 already has a copy of this shard (remember: a node cannot have duplicate shards of the same copy).

Each node in the cluster is scored by Elasticsearch’s allocation deciders when deciding where to place a shard.

weight_ranking is the rank of this node compared to others for placing this shard.

Lower numbers = better candidate
Higher numbers = less preferred

Elasticsearch uses several allocation deciders, like:

same_shard → prevents duplicate copies of the same shard on one node

disk_threshold → prevents allocation if the node doesn’t have enough disk

shard_balance → tries to distribute shards evenly across nodes

awareness / zone → ensures shards are balanced across availability zones

Each node gets scores from these deciders, and then weight_ranking is assigned:

1 = best fit
2, 3… = less fit

Conclusion:
When ES decides where to allocate or move a shard, it prefers nodes with the lowest weight_ranking.
If can_rebalance_to_other_node: no and the weight_ranking of current node is 1, it basically means:
“This shard is already on the optimal node — no other node is better.”
