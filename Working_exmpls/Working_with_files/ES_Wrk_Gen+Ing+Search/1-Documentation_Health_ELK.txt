generate_reports.py — Generates data
10 distinct ailment profiles (Diabetes, Hypothyroidism, Iron-Deficiency Anaemia, CKD Stage 3, Liver Cirrhosis, 
Hypertensive Heart Disease, Allergic Asthma, Bacterial Sepsis, PCOS, Rheumatoid Arthritis), each with realistic abnormal lab values. 

It cycles through all 10 across 50 patients and applies small random jitter to each numeric value so the reports aren't identical twins.
Each PDF is chunked by section (CBC, Thyroid, Metabolic, etc.), so a search for "elevated TSH" hits the Thyroid 
chunk rather than an entire document. Abnormal tests are extracted and stored as a keyword array — perfect for 
Elasticsearch term aggregations and bucket analytics.

Use the generated Lab reports from : E:\lab_reports

===========================================
Analytical queries — term aggregations over abnormal_tests (which conditions co-occur?), avg_abnormal_count bucketed by diagnosis, 
specialty-level heatmaps, and patient-level lookups by patient_id. These are pure ES aggregations — fast and pre-indexed.

Search queries — full-text on chunk_text and diagnosis with fuzzy matching, filtered by section (e.g. only Thyroid chunks), 
boosted by abnormal_tests, and deduplicated per patient. The highlight field gives us contextual snippets.

Visualizations: we can build — diagnosis distribution (bar/pie), abnormal test frequency (horizontal bar), average abnormal count 
per condition (grouped bar), per-specialty breakdowns, and scatter plots of individual patients colored by condition.

Examples:
Full-text search — fuzzy
> python es_ingest.py --search "elevated TSH hypothyroid"
Hits Thyroid Function chunks. Fuzzy matching catches misspellings. Returns best chunk per patient with highlighted context.

Explaination:
Why 285 total hits? The "size": 0 only suppresses returning individual documents in the hits array — but hits.total.value always 
reports the full document count that the query matched. Since we have no query clause (just aggs), 
it matches every document in the index: all 285 chunks. The aggregation then runs over all 285 of those. This is expected and correct.
Why does doc_count show 30/25, not 5? Each of our 5 patients per diagnosis contributes ~6 section chunks each:

8 diagnoses × 5 patients × 6 chunks = 30 docs per bucket
2 diagnoses with slightly fewer sections = 25 docs per bucket

So doc_count: 30 doesn't mean 30 patients — it means 30 chunks belonging to that diagnosis. The avg_abn is averaging 
abnormal_count across all those chunks, including the Header and Interpreting Physician sections which have 0 abnormal tests. 
That's why the averages look low (0.67–2.0) rather than reflecting the true per-patient abnormal count.

##abnormal count per patient, not per chunk
So > To get a more meaningful average — abnormal count per patient, not per chunk — we should filter 
to one representative chunk, like section: "Header" or use a max sub-aggregation instead of avg.

GET lab_reports/_search
{
  "size": 0,
  "aggs": {
    "by_diagnosis": {
      "terms": { "field": "diagnosis.keyword", "size": 20 },
      "aggs": {
        "avg_abn": { "avg": { "field": "abnormal_count" } },
        "max_abn": { "max": { "field": "abnormal_count" } },
        "patient_count": { "cardinality": { "field": "patient_id" } }
      }
    }
  },
  "query": {
    "bool": {
      "must_not": [
        { "terms": { "section": ["Header", "Interpreting Physician"] } }
      ]
    }
  }
}

Note**
This excludes the zero-flag structural sections so the average reflects only clinical test sections. The cardinality sub-agg also gives 
us the true unique patient count per bucket as a sanity check — it should return 5 for every diagnosis.

##Co-occurrence — patients with 2+ specific flags
Finds patients flagged for both HbA1c and microalbumin — 
classic diabetic nephropathy pattern. Combine with a term on section to restrict to the relevant chunk.
GET lab_reports/_search
{
  "query": {
    "bool": {
      "filter": [
        { "terms": { "abnormal_tests": ["HbA1c", "Microalbumin"] } },
        { "range": { "abnormal_count": { "gte": 2 } } }
      ]
    }
  }
}

##Section-filtered search
Restrict to a specific section chunk to avoid false positives from Header or CBC sections.
GET lab_reports/_search
{
  "query": {
    "bool": {
      "must": { "match": { "chunk_text": "microalbumin nephropathy" } },
      "filter": { "term": { "section": "Diabetes & Renal" } }
    }
  },
  "highlight": { "fields": { "chunk_text": {} } }
}

Find all chunks where a specific test was flagged. Exact keyword match on the array field.

{

  "_source": ["patient_name", "patient_id", "diagnosis", "abnormal_tests"]
}

##Co-occurrence — multiple abnormal flags
Patients with both HbA1c and Microalbumin flagged — classic diabetic nephropathy pattern.

        { "terms": { "abnormal_tests": ["HbA1c", "Microalbumin"] } },

      ]
    }
  }
}

##Range query — high abnormal_count chunks
Find section chunks with 3 or more abnormal tests — the most lab-severe patients.
GET lab_reports/_search
{
  "query": { "range": { "abnormal_count": { "gte": 3 } } },
  "sort": [{ "abnormal_count": "desc" }],
  "_source": ["patient_id", "patient_name", "section", "abnormal_count", "abnormal_tests"]
}

##Semantic
[Every query deliberately avoids the actual indexed terms. "Sluggish thyroid making someone cold and tired" doesn't appear anywhere in our data,

##Traps
[The four failure modes specific to all-MiniLM-L6-v2: 
single-word vague queries, 
numeric threshold reasoning (the model can't compare 14.6 > 10), 
negation (embeddings of "with kidney problems" and "without kidney problems" are nearly identical vectors), 
and ambiguous cross-condition symptoms like "fatigue and anaemia" which match 5 of our 10 conditions.
]

#These queries look semantic but will give poor or misleading results with all-MiniLM-L6-v2. 
#Single-word vague queries
"Inflammation" embeds to a generic vector that's equidistant from Sepsis, RA, Asthma, and CKD. 
we'll get low-confidence results across all conditions. Add context.

python es_ingest_semantic.py --semantic "inflammation" # too vague
python es_ingest_semantic.py --hybrid "acute bacterial infection with systemic inflammation" # better

#Queries with numbers and thresholds
all-MiniLM-L6-v2 doesn't understand numeric reasoning. "TSH greater than 10" doesn't vector-match to TSH 14.6 better than 
TSH 2.4 — the model sees "TSH" in both. Use a range query in ES for numeric filtering.

python es_ingest_semantic.py --semantic "TSH greater than 10" # model ignores the number

--Use ES range query instead: 
GET lab_reports_semantic/_search { "query": { "range": { "abnormal_count": { "gte": 3 } } } }

#Negation queries
"Patient without kidney problems" embeds almost identically to "patient with kidney problems" — transformers don't reliably encode negation.
 Use a must_not bool filter for exclusion.

python es_ingest_semantic.py --semantic "patient without kidney problems" # negation ignored

GET lab_reports_semantic/_search { "query": { "bool": { "must_not": { "terms": { "abnormal_tests": ["Creatinine", "eGFR", "BUN"] } } } } }
