#Aggregation /Sorting functonalities
#Sorting data
using sort we can add one or more sorts on specific fields, where in each sort can be reversed.
sort is defined per field level with field name '_score' to sort by score and optionally '_doc' to sort based on index order

GET /bankdata/_search
{
  "sort": [
    {"age": {"order": "asc"}},
    {"balance": {"order": "desc"}},
    "_score"],
    "query": {
      "term": {
        "age": {
          "value": "75"
        }
      }
    }
}

Filters documents where age == 75 (term = exact match).
Sorts results by:
age ascending (youngest → oldest, though all are 75 here)
then by balance descending (richest first)
then by relevance score (_score)

Considerations:
term query does not analyze the value — it’s an exact numeric match (perfect for age).
_score only applies to full-text queries, but you can still include it as a tie-breaker.

#Sort Using Mode (for arrays or multiple values)

GET /bankdata/_search
{
  "query": {
      "term": {
        "age": {
          "value": "75"
        }
      }
    },
  "sort": [
    {"balance": {"order": "asc",
    "mode": "avg"}}
  ]  
}

but if balance is an array (e.g. multiple account balances),
Elasticsearch uses the average of all values to sort.
| Mode     | Meaning                     |
| -------- | --------------------------- |
| `min`    | Use lowest value in array   |
| `max`    | Use highest value           |
| `avg`    | Use average                 |
| `sum`    | Use sum                     |
| `median` | Available in newer versions |

Note**Elasticsearch stops counting hits after 10,000 documents by default.
The "gte" (greater than or equal) relation means there are more than 10,000 documents, but it didn’t count beyond that limit.

The index.max_result_window (default = 10,000) protects the cluster from:

High memory use
Deep pagination scans
Overly expensive queries

Options to Handle Large Result Sets / Pagination

1. Use Composite Aggregations (Best for Large Buckets)
Composite aggregations allow paginated aggregations, meaning you can fetch results in batches.

GET /bankdata/_search
{
  "size": 0,
  "aggs": {
    "education_group": {
      "composite": {
        "size": 1000,
        "sources": [
          { "education": { "terms": { "field": "education.keyword" } } }
        ]
      },
      "aggs": {
        "avg_balance": { "avg": { "field": "balance" } },
        "avg_age": { "avg": { "field": "age" } }
      }
    }
  }
}

If there are more than 1000 buckets, Elasticsearch will return:
"after_key": { "education": "some_value" }

concluding:
| Feature        | What it Does                         | Type               |
| -------------- | ------------------------------------ | ------------------ |
| `term` query   | Exact match (no analysis)            | Filter             |
| `range` query  | Numeric comparison                   | Filter             |
| `sort`         | Orders results by one or more fields | Search result      |
| `mode`         | Handles multi-valued fields          | Sort               |
| `terms agg`    | Groups by unique categorical values  | Aggregation        |
| `range agg`    | Buckets by numeric range             | Aggregation        |
| `avg`, `stats` | Compute metrics                      | Metric aggregation |
| `top_hits`     | Return sample docs per bucket        | Sub-aggregation    |

#Managing state using policy
#defining a hot–warm–delete ILM/ISM policy for managing time-based or size-based index lifecycles — specifically for indices matching newtestlog*.

PUT _ilm/policy/mgmt_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": {
            "max_age": "1m",
            "max_primary_shard_size": "3mb",
            "max_docs": 1500
          }
        }
      },
      "warm": {
        "min_age": "1m",
        "actions": {
          "allocate": {
            "number_of_replicas": 5
          }
        }
      },
      "delete": {
        "min_age": "10m",
        "actions": {
          "delete": {}
        }
      }
    }
  }
}

ILM uses phases (hot, warm, delete) instead of states.
The keys are max_age, max_docs, etc., instead of min_index_age.
The warm phase transition is automatic when the min age is reached.

in OpenSearch


ISM Policy: mgmt_policy

This defines:
Hot phase: Active writes.
--Rolls over when:
	Index age ≥ 1m
	Primary shard size ≥ 3MB
	Document count ≥ 1500
  Then transitions to warm.
Warm phase: Reduced write activity, optimized for storage.
   Sets number_of_replicas to 5.
   After 10m (index age), transitions to delete.

Delete phase: Deletes the index.
The ism_template applies this policy automatically to all indices matching newtestlog*.

PUT /_plugins/_ism/policies/mgmt_policy?pretty
{
  "policy": {
    "description": "hot warm delete workflow",
    "default_state": "hot",
    "schema_version": 1,
    "states": [
      {
        "name": "hot",
        "actions": [
          {
            "rollover": {
              "min_index_age": "1m",
              "min_primary_shard_size": "3mb",
              "min_doc_count": 1500
            }
          }
        ],
        "transitions": [
          {
            "state_name": "warm"
          }
        ]
      },
      {
        "name": "warm",
        "actions": [
          {
            "replica_count": {
              "number_of_replicas": 5
            }
          }
        ],
        "transitions": [
          {
            "state_name": "delete",
            "conditions": {
              "min_index_age": "10m"
            }
          }
        ]
      },
      {
        "name": "delete",
        "actions": [
          {
            "delete": {}
          }
        ]
      }
    ],
    "ism_template": {
      "index_patterns": ["newtestlog*"],
      "priority": 500
    }
  }
}
