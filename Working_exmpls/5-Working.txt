GET /recipes/_search?q=Beef Chuck Roast
Explaination: simple query-string search
Equivalent:
GET /recipes/_search
{
  "query": {
    "query_string": {
      "query": "Beef Chuck Roast"
    }
  }
}

By default, it searches across all full-text fields in your recipes index (like name, description, and ingredients).
Elasticsearch uses the BM25 similarity algorithm to calculate the _score — the relevance of each document.
Each document’s score is based on:
--Term Frequency (TF): how often “Beef”, “Chuck”, and “Roast” appear.
--Inverse Document Frequency (IDF): how rare those terms are in the entire index.
--Field Length Normalization: shorter text fields (like name) are weighted more heavily than long fields (ingredients).

For document:
"name": "Drip Beef, Two Ways",
"ingredients": "1 whole Beef Chuck Roast..."

It scores very high (_score: 15.475) because:

“Beef” appears in both the title and ingredients
“Chuck” and “Roast” also appear in ingredients
These terms are close together in context.

GET /recipes/_search?q=Chuck Beef Roast

the same top documents appear with the same scores (15.475, 11.593, etc.).
Query-string search is tokenized, so word order doesn’t matter.
The analyzer breaks “Beef Chuck Roast” and “Chuck Beef Roast” into the same tokens:
["beef", "chuck", "roast"]

Since BM25 scoring is term-based, the order of words doesn’t change the results.

| Recipe Name                                     | Score  | Why it ranked high                                                                            |
| ----------------------------------------------- | ------ | --------------------------------------------------------------------------------------------- |
| **Drip Beef, Two Ways**                         | 15.475 | All three query terms (“Beef”, “Chuck”, “Roast”) appear multiple times, in short text fields. |
| **Beer-Braised Beef with Onions**               | 11.59  | Contains “Beef” and “Chuck Roast”.                                                            |
| **Spicy Stewed Beef with Creamy Cheddar Grits** | 11.59  | Has “Beef” and “Chuck Roast” in `ingredients`.                                                |
| **Italian Pot Roast**                           | 9.23   | Contains “Beef”, “Chuck”, “Roast”, but terms are farther apart.                               |
| **Hot Roast Beef Sandwiches**                   | 8.09   | Two words match but not “Chuck”.                                                              |

The _score is not absolute — it’s a relative measure within the query results only.
A higher _score = stronger match.

| Concept                             | Description                                                     |
| ----------------------------------- | --------------------------------------------------------------- |
| **Algorithm**                       | BM25 (term frequency, rarity, length normalization)             |
| **Default Search Type**             | `query_string` across all text fields                           |
| **Word Order**                      | Ignored (tokens matched individually)                           |

By default, Elasticsearch uses the standard analyzer for text fields.
The standard analyzer splits text on special characters — including @ and ..
So "rthomas4r@google.pl" gets tokenized into tokens like:
["rthomas4r", "google", "pl"]

that should match "google", right?
But it depends on how the field is mapped.

--probably field mapping here is keyword and not text
When we indexed those documents via the bulk API, Elasticsearch automatically inferred mappings from the JSON structure.
Because email looks like a structured, not a sentence-like field, Elasticsearch’s dynamic mapping rules would map it as a keyword field.

## “More Like This” (MLT) Query
Find recipes similar to “Italian Pot Roast”.
GET /recipes/_search
{
  "query": {
    "more_like_this": {
      "fields": ["name", "description", "ingredients"],
      "like": [
        { "_id": "JbXZvJkBP7cbH4icpkAI" }  // ID of "Italian Pot Roast"
      ],
      "min_term_freq": 1,
      "max_query_terms": 12
    }
  }
}

Elasticsearch magic:
It analyzes that recipe’s text and builds a “fingerprint” of important terms to find others with similar ingredient patterns.
Fingerprint:
When we run query:

It Fetches that document from our index (the "Italian Pot Roast" recipe).
Runs it through the same text analyzers that are used for search (tokenizing, lowercasing, removing stop words, etc.).
Counts how often each term appears in that document (term frequency, TF).
Looks up how common those same terms are across the entire index (inverse document frequency, IDF).
Keeps the most distinctive words — the ones that define this document and make it unique compared to others.
Builds a query out of those “important” words.
Those top distinctive terms together form what we call a fingerprint of that document’s content.

Example:
Name: Italian Pot Roast
Ingredients:
Beef Chuck Roast  
Roasted Red Peppers  
Artichoke Hearts  
Sundried Tomatoes  
Beef Stock  
Garlic  
Wine

After analyzing, Elasticsearch might extract tokens like:
["beef", "roast", "artichoke", "tomatoes", "garlic", "wine"]

it looks across all recipes and asks: > 
Which other recipes contain many of these terms, in similar proportions?

That “vector” of important terms — beef, roast, garlic, wine, tomatoes — becomes the semantic fingerprint for this recipe.
So if another recipe shares many of those rare, distinctive terms (say, “Beer-Braised Beef with Onions” or “Drip Beef, Two Ways”), it will score high on similarity.

Under the hood:
TF (term frequency): Words that appear often in this recipe are important.
IDF (inverse document frequency): Words that are rare across the index (e.g., “artichoke”) get more weight than common words (e.g., “beef”).
Result: The top max_query_terms words are used to build a new BM25-based query.

Elasticsearch implements “similar documents” or “recommendations” — like “More like this recipe.”

## Weighted Query — Boost “easy” or “quick” recipes
Boost recipes whose descriptions mention “quick” or “easy”.
GET /recipes/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "ingredients": "beef" } },
      "functions": [
        {
          "filter": { "match": { "description": "quick" } },
          "weight": 2
        },
        {
          "filter": { "match": { "description": "easy" } },
          "weight": 2
        }
      ],
      "score_mode": "sum",
      "boost_mode": "multiply"
    }
  }
}

Elastic magic:
Combines textual relevance with dynamic weighting → “smart ranking”.

More on "Smart Ranking"
ES doesn’t just find documents — it can rank them intelligently based on context, text relevance, metadata, and even custom logic we design.

Every document that matches our query gets a _score — a relevance score calculated (by default) using BM25, based on:

How often the search terms appear in the document (term frequency)
How rare those words are across all documents (inverse document frequency)
How short the field is (length normalization)

But with ES,it lets us control and enhance this ranking using function scores, boosting, and hybrid logic, 
to reflect our business rules or domain intuition.

1.Field Boosting — “Title matters more than description”
> tell Elasticsearch which fields are more important
For example:
GET /recipes/_search
{
  "query": {
    "multi_match": {
      "query": "beef roast",
      "fields": [
        "name^3",          // title = 3× weight
        "description^1",
        "ingredients^2"
      ]
    }
  }
}

--Smart Ranking logic:
A recipe where “beef roast” is in the name ranks higher than one where it’s only in the description.

2.Function Score — Custom Boosts Based on Metadata
> Boost recipes that are quick to cook or recently published:
GET /recipes/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "ingredients": "beef" } },
      "functions": [
        {
          "filter": { "range": { "cookTime.keyword": { "lte": "PT1H" } } },
          "weight": 3
        },
        {
          "filter": { "range": { "datePublished": { "gte": "2020-01-01" } } },
          "weight": 2
        }
      ],
      "score_mode": "sum",
      "boost_mode": "multiply"
    }
  }
}

Result:
Each matching doc gets a base BM25 _score.
Then, if it’s quick to cook, it gets ×3 weight.
If it’s recent, it gets ×2.
Elasticsearch multiplies/combines these to produce a smarter _score.
So a new, quick beef recipe outranks a 2010 one that takes 5 hours to cook

3. Script Scoring — Write Your Own Formula
>define a custom mathematical formula for ranking.
--prefer recipes that use fewer ingredients and cook faster.

GET /recipes/_search
{
  "query": {
    "script_score": {
      "query": { "match": { "ingredients": "beef" } },
      "script": {
        "source": """
          double base = _score;
          double cookBoost = doc['cookTime.keyword'].value == 'PT1H' ? 2 : 1;
          double complexityPenalty = 1.0 / (doc['ingredients'].size() + 1);
          return base * cookBoost * complexityPenalty;
        """
      }
    }
  }
}

Smart Ranking logic:

Base text relevance (_score) ×
Boost for fast cook times ×
Penalize complex recipes (many ingredients)
