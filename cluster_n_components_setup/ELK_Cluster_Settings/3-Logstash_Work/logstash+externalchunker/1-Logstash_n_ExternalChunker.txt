Logstash n external chunker script
==================================
Structured Data:
Lab reports (pdf_chunked_pipeline.conf + pdf_chunker.py)

Structured section splitting on known headers (CBC, Thyroid, Metabolic etc.)
Patient metadata extraction (patient_id, diagnosis, abnormal_tests)
Index: lab-reports-chunks
Folder: <path>/lab_reports

-------------------------------------------
Keep Logstash for discovery + routing, do the chunking in a custom Ruby script that shells out to Python, 
then send pre-chunked events back through Logstash's http input or directly to ES. Clean separation of concerns.
Rewrite the pipeline so Logstash handles file watching + metadata and a Python ingest pipeline script 
(for example: our es_ingest_semantic.py) does the heavy lifting — Logstash triggers it via exec. 

File discovery      Old:exec + find runs every hour, re-processes everything             New:file input with sincedb — only picks up new/changed PDFs
Chunking            Old:Base64-encoded the whole PDF binary, sent to ES ingest pipeline  New: Python chunker extracts text, splits into N chunks, returns JSON lines
One doc per PDF     Old:our ingest pipeline had to handle everything                     New:One ES document per chunk, fan-out via split filter
Duplicate prevention Old: None                                                           New:SHA1 fingerprint of filename + chunk_index as document_id — re-running upserts, no duplicates

So now we can
PDF folder
    │
Logstash file input (sincedb watches for new PDFs)
    │
Ruby filter → Open3.capture3("python3 pdf_chunker.py /path/to/file.pdf")
    │
pdf_chunker.py writes N JSON lines to stdout (one per chunk)
    │
Ruby parses lines → event.set("chunks", [...])
    │
split filter → N separate Logstash events
    │
Elasticsearch (lab-reports-chunks index, one doc per chunk)

Two modes in pdf_chunker.py — change MODE at the top:

"structured" — uses your existing section header logic (CBC, Thyroid, Metabolic etc.) — best for your lab reports
"fixed" — 1000-char overlapping windows with 200-char overlap — use this for the BI_approaches.pdf style generic PDFs you had earlier

To enable embeddings later, just flip EMBED = True in pdf_chunker.py and make sure the ES index mapping 
has the dense_vector field (copy from es_ingest_semantic.py).

=====================================
Summarizing:
Pure Python (es_ingest_semantic.py)
✓
Full control over every chunking decision — you wrote the logic, you debug it in Python
✓
sentence-transformers, pdfplumber, spaCy — any library, no JVM restrictions
✓
Easy to test:
python script.py --search "query"
— immediate feedback
✓
Embeddings computed inline — no shell-out overhead, model loaded once
Single file to maintain, no YAML + Ruby + Python split across 3 files
✓
Error tracebacks are Python — readable, stack-traceable
✗
No built-in file watching — you run it manually or schedule via cron
✗
No automatic retry on ES failure — you'd add that yourself
✗
Not part of a broader ELK observability stack if you're using one

Logstash + Python chunker
✓
sincedb tracks processed files — new PDFs auto-ingested without re-running anything
✓
Built-in retry, dead letter queue, back-pressure handling
✓
Fits naturally into existing ELK stack — Kibana can monitor pipeline health
✓
Can fan out to multiple outputs (ES + S3 + Kafka) in one config
✗
Ruby filter calls Python via Open3 shell-out — each PDF spawns a new process
Embedding model reloads per PDF (unless you run a persistent embedding server)
✗
Debugging across Ruby + Python + YAML is painful — errors in 3 different places
✗
Logstash uses ~500MB RAM just to run, even for a tiny pipeline
✗
JVM startup adds 10–20s lag before any processing begins

The hidden cost: model reloading
With Logstash, every PDF triggers Open3.capture3("python3 chunker.py file.pdf"). 
Python starts fresh, imports pdfplumber, imports sentence-transformers, loads the 80MB model weights from disk, processes the file, exits. 
For 3 PDFs that's 3 cold starts. 
For 50 lab report PDFs that's 50 cold starts — easily 3–5 minutes of model loading vs 30 seconds if the model is loaded once in Python.

Complexity comparison
Files you need to maintain:
> es_ingest_semantic.py

Logstash approach
academic_pdf_pipeline.conf (Logstash DSL)
academic_pdf_chunker.py (Python)
sincedb file (auto-created)
completed log file (auto-created)
Total: 4 files, 2 languages

The one genuine reason to keep Logstash in setup is if we already have it running for something else 
(application logs, system metrics etc.) and want a single place to manage all pipelines. 
If we're running Logstash purely for PDF ingestion, it's adding JVM overhead, 500MB RAM, 
and a two-language debugging problem for no real gain over Python.

Suggestion:
Add watchdog (pip install watchdog) if needed- auto-pickup of new files — 10 lines which then replaces the entire Logstash pipeline.

        "k": 5, "num_candidates": 50
    },
    "_source": ["doc_title", "section", "chunk_text"]
})
for h in resp["hits"]["hits"]:
